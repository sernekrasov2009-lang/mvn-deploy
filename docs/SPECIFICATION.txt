===============================================================================
0. КРАТКОЕ ОПИСАНИЕ
===============================================================================

MVN Deploy — небольшой open-source инструмент для автоматической подготовки
чистого Linux VPS под личный VPN-сервер. Основой служит существующий проект
3x-ui, который управляет Xray-core и предоставляет веб-панель для дальнейшей
настройки сервера.

Главный принцип: MVN Deploy НЕ должен повторно реализовывать возможности 3x-ui.
Он должен безопасно и предсказуемо выполнить первичную настройку системы,
установить 3x-ui официальным способом, настроить требуемые системные параметры,
проверить результат и показать администратору, что получилось.

Целевой пользовательский сценарий:

  1. Арендовать новый VPS.
  2. Подключиться к нему по SSH.
  3. Выполнить одну команду установки MVN Deploy.
  4. Ответить на несколько действительно необходимых вопросов, если они нужны.
  5. Дождаться автоматической настройки.
  6. Получить адрес панели, способ узнать логин/пароль и итоговый статус.
  7. Создавать и управлять VPN-подключениями уже внутри 3x-ui.

Ожидаемый результат — подготовленный сервер, на котором установлена и работает
3x-ui с управляемым ею версией Xray-core, включён BBR, настроен локальный
межсетевой экран по согласованным правилам и выполнены базовые проверки.

Важно: на дату документа текущий репозиторий всё ещё является каркасом. Наличие
файла или успешного коммита не означает, что соответствующая функция реализована
и протестирована на реальном VPS.

===============================================================================
1. ЦЕЛИ ПРОЕКТА
===============================================================================

1.1. Главная цель
----------------

Развернуть повторяемую базовую конфигурацию VPN-сервера одной командой, не
заставляя пользователя вручную выполнять десятки команд на Linux.

1.2. Практические цели
----------------------

- Поддержать чётко определённый список Linux-дистрибутивов и архитектур.
- Проверять совместимость системы до любых существенных изменений.
- Устанавливать 3x-ui из официального источника проекта.
- Не устанавливать отдельный независимый Xray поверх Xray, которым управляет
  3x-ui.
- Автоматически подготовить firewall, сохранив доступ по SSH.
- Включить BBR, только если используемое ядро его поддерживает.
- Выполнить базовые проверки сервисов, сетевых портов и конфигурации.
- Показать понятный итог, а не просто закончить скрипт без объяснений.
- Вести журнал установки, не записывая секреты в открытый лог.
- Не ломать повторным запуском уже настроенный сервер.
- Обеспечить читаемую структуру, документацию, тесты и понятную историю Git.

1.3. Принципы
--------------

- Простота: один обычный сервер, без сущностей «master», «node» и сложных схем.
- Минимум магии: каждый системный шаг объясним и проверяем.
- Безопасность по умолчанию: не менять SSH так, чтобы можно было потерять доступ.
- Прозрачность: перед потенциально опасным действием сообщать, что изменится.
- Идемпотентность: повторный запуск не должен случайно дублировать настройки.
- Разделение ответственности: 3x-ui управляет панелью и Xray; MVN Deploy —
  установкой и системной подготовкой.
- Проверяемость: успешная команда сама по себе не считается доказательством успеха.

===============================================================================
2. ЧТО ВХОДИТ В ПРОЕКТ
===============================================================================

В область ответственности MVN Deploy входят:

1. Проверка ОС, версии, архитектуры, прав доступа, systemd, apt и сети.
2. Установка обязательных системных утилит.
3. Запуск официального установщика 3x-ui.
4. Обеспечение того, что 3x-ui и его сервис доступны после установки.
5. Базовая настройка firewall с учётом SSH, панели и выбранных портов.
6. Включение и проверка TCP BBR, если оно поддерживается ядром.
7. Сбор технических результатов установки и выдача итогового отчёта.
8. Документация, проверка кода, диагностика и безопасное обновление самого MVN Deploy.

3x-ui отвечает за:

- веб-панель управления;
- собственный systemd-сервис и управление его состоянием;
- установку и эксплуатацию Xray-core согласно поддерживаемому способом установки;
- конфигурацию inbound/outbound и протоколов в панели;
- создание клиентов, статистику, выдачу ссылок и QR-кодов при использовании
  соответствующих возможностей самой панели;
- обновление и внутренние настройки 3x-ui через поддерживаемые механизмы проекта.

===============================================================================
3. ЧТО ОСОЗНАННО НЕ ВХОДИТ В ПЕРВУЮ ВЕРСИЮ
===============================================================================

MVN Deploy НЕ должен:

- создавать собственную VPN-панель;
- генерировать отдельные VLESS-ссылки, UUID, QR-коды или клиентские файлы;
- создавать дополнительных Linux-пользователей для VPN-клиентов;
- самостоятельно создавать пользователей/клиентов внутри 3x-ui;
- формировать собственный /usr/local/etc/xray/config.json;
- создавать отдельный xray.service, который конфликтует с 3x-ui;
- реализовывать собственную систему подписок и учёта трафика;
- строить мультисерверную архитектуру, узлы, master/node или балансировщик;
- ставить Docker в первой версии без отдельной необходимости;
- самостоятельно менять облачный firewall у провайдера VPS — это внешняя
  инфраструктура, доступ к которой у обычного root на гостевой ОС может отсутствовать;
- без предупреждения менять SSH-порт, запрещать root login, отключать вход по
  паролю или перезагружать сервер;
- считать открытие типовых портов заменой проверки реальных портов приложения.

Пользователь сможет отдельно создать inbound и клиента через интерфейс 3x-ui.
MVN Deploy лишь подготавливает систему для этого.

===============================================================================
4. БАЗОВАЯ ПЛАТФОРМА И ПОДДЕРЖИВАЕМЫЕ СИСТЕМЫ
===============================================================================

4.1. Предлагаемый первый целевой набор
--------------------------------------

В качестве начальной проверяемой матрицы предлагаются:

- Debian 12 и Debian 13;
- Ubuntu 22.04 LTS и Ubuntu 24.04 LTS;
- архитектуры amd64 (x86_64) и arm64 (aarch64), если выбранные релизы 3x-ui
  официально доступны и фактически протестированы на обеих архитектурах.

Этот перечень является целевым, а не утверждением о текущем состоянии кода.
Окончательный список фиксируется по результатам тестов. Скрипт обязан завершить
работу с понятной ошибкой на неподдерживаемой системе, а не подбирать бинарник
наугад.

4.2. Требования к VPS
---------------------

- Доступ root или возможность надёжно получить root через sudo.
- Рабочий пакетный менеджер apt на поддерживаемых Debian/Ubuntu.
- systemd и systemctl.
- Доступ к официальным репозиториям ОС и GitHub.
- Корректное системное время.
- Свободное место для пакетов, программы, конфигурации и журналов.
- Возможность создать/изменить правила локального firewall.

Если у VPS есть отдельный firewall в панели провайдера, пользователь должен
проверить его независимо. Скрипт на самом VPS не должен утверждать, что изменил
внешний firewall, если у него нет интеграции с API провайдера.

===============================================================================
5. ПОЛЬЗОВАТЕЛЬСКИЙ СЦЕНАРИЙ УСТАНОВКИ
===============================================================================

5.1. Команда установки
----------------------

Установщик должен поддерживать однострочный запуск с GitHub. В финальном релизе
предпочтителен version-pinned путь, например:

  curl -fsSL https://raw.githubusercontent.com/sernekrasov2009-lang/mvn-deploy/v1.0.0/install.sh -o /tmp/mvn-deploy-install.sh && bash /tmp/mvn-deploy-install.sh

Версия v1.0.0 здесь пример будущего релиза, а не существующий релиз.
Во время разработки можно использовать ветку main, однако она изменяема и потому
хуже подходит для воспроизводимых production-установок.

Критически важно: если install.sh загружается как единственный файл, он не может
просто предположить, что рядом уже находятся scripts/, config/ и templates/.
Bootstrap-скрипт должен получить соответствующую версию всего проекта в рабочую
директорию (например, из релизного архива), проверить её и только потом вызвать
основной код. Иначе команда «скачать один install.sh» не сможет найти остальные
модули.

Для публикации следует использовать релизы/теги, фиксированную ссылку на исходники
и проверку контрольной суммы релизного архива. Во время разработки загрузку из
main разрешать только осознанно.

5.2. Что пользователь должен увидеть
------------------------------------

Пример вывода — иллюстрация желаемого формата, не реальный вывод текущего кода:

  MVN Deploy — One-command VPN Server Deployment
  [INFO] Checking operating system...
  [ OK ] Supported OS detected
  [ OK ] Root access confirmed
  [INFO] Checking existing services and firewall...
  [ OK ] SSH access rule prepared
  [INFO] Installing required packages...
  [ OK ] Dependencies installed
  [INFO] Installing 3x-ui using the official installer...
  [ OK ] 3x-ui service is active
  [INFO] Configuring TCP BBR...
  [ OK ] BBR is enabled
  [INFO] Verifying ports and services...
  [ OK ] Basic checks passed

  Deployment completed.
  Panel address: <detected-address-and-port>
  Credentials: see the protected installation result / official x-ui menu
  Log file: /var/log/mvn-deploy/install.log

Реальный вывод не должен показывать пароли, токены или приватные ключи в общем
логе. Секреты выводятся только в специально отведённом финальном блоке, если это
необходимо, и должны храниться на диске с правами только для root.

5.3. Вопросы пользователю
-------------------------

Первая версия должна быть максимально автоматической, но не должна гадать в
опасных местах. При необходимости она спрашивает только конкретные настройки:

- подтверждение изменения firewall, если на сервере уже существует активная
  политика или правила, которые невозможно безопасно распознать;
- SSH-порт, если его невозможно надёжно определить;
- нужно ли выполнять необязательное полное обновление пакетов ОС;
- дополнительные TCP/UDP-порты, если пользователь хочет открыть их сейчас;
- решение о продолжении, если обнаружена уже установленная панель или другой
  VPN-сервис, который может конфликтовать.

В unattended-режиме значения должны передаваться через переменные окружения или
файл конфигурации. В этом режиме опасное неоднозначное действие должно завершаться
ошибкой, а не молча угадываться.

6. АРХИТЕКТУРА ПРОЕКТА
===============================================================================

Предлагаемая целевая структура:

  mvn-deploy/
  |
  |-- install.sh
  |-- update.sh
  |-- uninstall.sh
  |-- README.md
  |-- LICENSE
  |-- .gitattributes
  |-- .gitignore
  |-- config/
  |   `-- defaults.conf
  |-- scripts/
  |   |-- logger.sh
  |   |-- system.sh
  |   |-- dependencies.sh
  |   |-- security.sh
  |   |-- firewall.sh
  |   |-- bbr.sh
  |   |-- three_x_ui.sh
  |   `-- verify.sh
  |-- docs/
  |   |-- INSTALL.md
  |   |-- TROUBLESHOOTING.md
  |   `-- SECURITY.md
  `-- tests/
      |-- lint.sh
      `-- fixtures/ (если понадобятся)

Названия модулей можно менять по ходу разработки, но назначение каждого файла
должно оставаться ясным. Необязательно создавать отдельный скрипт для каждой
команды. Дополнительные файлы создаются только при наличии отдельной обязанности.

6.1. install.sh — bootstrap и оркестратор
-----------------------------------------

Ответственность:

- определить версию/ветку, из которой выполняется установка;
- загрузить и проверить полный набор исходников, если запуск пришёл с GitHub;
- проверить root, Bash, совместимость и наличие нужных команд;
- включить строгий режим обработки ошибок;
- подключить logger и config;
- выполнить модули в правильном порядке;
- перехватить ошибку и вывести, на каком этапе произошёл сбой;
- не запускать следующие этапы после неудачного критического этапа;
- по завершении вызвать verify.sh и вывести итоговый отчёт.

Рекомендуется использовать строгий режим наподобие set -Eeuo pipefail, аккуратный
trap для ошибок, блокировку от параллельного запуска и проверку exit code каждого
модуля. Строгий режим надо применять осмысленно: скрипты не должны скрывать ошибки,
но допустимые необязательные проверки должны обрабатываться явно.

6.2. logger.sh — единый вывод и журнал
--------------------------------------

Функции:

- log_info — обычное сообщение;
- log_ok — успешный шаг;
- log_warn — предупреждение;
- log_error — ошибка;
- единый формат с датой/временем для файла журнала;
- ANSI-цвета только при подходящем терминале;
- отсутствие цветов и интерактивных управляющих последовательностей в файле;
- секреты не должны автоматически попадать в журнал.

Целевой журнал: /var/log/mvn-deploy/install.log. Каталог и файл создаются с
ограниченными правами. Если запись в журнал недоступна, скрипт сообщает об этом.
Не следует писать туда пароли панели, токены, приватные ключи и полное содержимое
секретных файлов.

6.3. config/defaults.conf — настройки
-------------------------------------

В конфигурации допустимы только параметры, реально используемые проектом, например:

- PROJECT_NAME и VERSION;
- поддерживаемые ОС и архитектуры;
- список дополнительных портов;
- включает ли пользователь применение BBR;
- путь к логу;
- режим установки/обновления;
- версия/канал 3x-ui, если проект будет поддерживать выбор версии.

Конфиг — доверенный Bash-код, поэтому его нельзя скачивать из непроверенного
источника и исполнять без проверки. Переменные и массивы должны быть объявлены
безопасно; ввод пользователя нужно валидировать перед использованием в командах.
Не следует подставлять ввод непосредственно в команды через eval.

6.4. system.sh — проверка ОС и окружения
---------------------------------------

Проверяет:

- наличие и читаемость /etc/os-release;
- ID, VERSION_ID и архитектуру;
- root-права;
- systemd/systemctl;
- apt и доступность пакетного менеджера;
- свободное место и базовую доступность сети;
- наличие уже установленных 3x-ui/Xray/других панелей;
- текущее состояние SSH и firewall перед изменениями;
- является ли запуск повторным.

Результат — понятное решение continue/abort и список замечаний. На неподдерживаемой
ОС работа прекращается до установки пакетов и редактирования сетевых правил.

6.5. dependencies.sh — системные зависимости
---------------------------------------------

Устанавливает только необходимые пакеты. В качестве возможных зависимостей могут
понадобиться ca-certificates, curl, wget, jq, tar, coreutils, iproute2, openssl,
ufw и утилиты, используемые проверками. Окончательный список формируется по коду.

Правила:

- выполнять apt-get update;
- проверять код возврата;
- не продолжать, если установка обязательных зависимостей провалилась;
- не делать полный apt upgrade без явно согласованной политики;
- не удалять пользовательские пакеты;
- по возможности избегать ненужной зависимости от jq, если та же задача надёжно
  решается средствами Bash/coreutils.

6.6. three_x_ui.sh — установка 3x-ui
------------------------------------

Это единственный модуль MVN Deploy, который непосредственно запускает установщик
3x-ui. Он должен использовать официальный источник проекта, описанный в разделе
«Источники и актуальность» в конце документа.

Требования:

- не скачивать сторонние «перепакованные» сборки;
- не устанавливать Xray вручную отдельным независимым способом;
- не создавать свой xray.service или свой конфиг Xray;
- зафиксировать и проверить применяемый способ установки;
- поддерживать выбранную версию официального установщика;
- после установки проверить наличие службы x-ui и результат её запуска;
- сохранить доступы, выданные официальным установщиком, безопасным способом;
- не считать сам факт завершения installer script подтверждением готовности;
- если формат файла с результатом или поведение upstream изменились, выдавать
  понятную ошибку и предлагать штатный способ узнать учётные данные, а не пытаться
  угадывать поля или показывать случайные значения.

На момент составления спецификации в официальном README 3x-ui описан запуск
официального install.sh, возможность указать тег версии и неинтерактивная установка
через XUI_NONINTERACTIVE=1; результат установки сохраняется upstream-скриптом в
/etc/x-ui/install-result.env. Эти детали нужно заново проверить и протестировать
перед выпуском каждой версии MVN Deploy, так как upstream может их изменить.

6.7. firewall.sh — управление локальным firewall
-------------------------------------------------

Firewall настраивается только после того, как собрана информация о реальных портах.
В частности, нельзя включать политику deny incoming, пока не разрешён фактический
SSH-порт текущего подключения.

Обязательный порядок:

1. Обнаружить активный firewall (UFW, nftables, firewalld или другое решение).
2. Если уже действует незнакомая политика, не сбрасывать её и не включать UFW
   поверх неё без понятного решения.
3. Определить SSH-порт из конфигурации/эффективного состояния sshd и проверить
   результат. Если определить достоверно нельзя — спросить пользователя.
4. Перед включением UFW разрешить SSH-порт и подтвердить наличие правила.
5. Разрешить только выбранные и нужные порты панели и VPN.
6. Применить правила только после проверки набора правил.
7. Считать firewall настроенным лишь после проверки итогового состояния UFW.

В конфигурации должны быть отдельно представлены TCP- и UDP-порты. В качестве
потенциальных портов могут рассматриваться SSH, порт веб-панели, а также выбранные
пользователем VPN/inbound-порты, например 443/tcp. Нельзя безусловно открывать
80, 443, 2053, 2096 и все прочие типовые порты без связи с конфигурацией сервера.
Порты inbound, которые пользователь создаст позже в 3x-ui, могут потребовать
дополнительного изменения firewall.

Критически важно:

- не удалять существующие правила вслепую;
- не делать flush всех iptables/nftables правил;
- не менять SSH-порт автоматически;
- не закрывать доступ к панели до проверки её реального порта;
- не утверждать, что внешний firewall провайдера изменён;
- сообщить, какие порты открыты и зачем;
- предусмотреть rollback или безопасный отказ до включения новой политики.

6.8. bbr.sh — включение TCP BBR
--------------------------------

Задача — проверить поддержку BBR используемым ядром и, если поддержка есть,
включить congestion control BBR и рекомендуемый для этого сценария qdisc fq.
Точные параметры фиксируются на основе доступной поддержки ядра.

Ожидаемый алгоритм:

1. Проверить net.ipv4.tcp_available_congestion_control.
2. Если bbr не поддерживается — вывести предупреждение, не ломать сетевые
   настройки и продолжить только в соответствии с политикой проекта.
3. Создать отдельный sysctl-файл, например /etc/sysctl.d/99-mvn-deploy-bbr.conf,
   вместо бездумного редактирования большого sysctl.conf.
4. Загрузить настройки через sysctl --system или эквивалентную проверенную команду.
5. Проверить фактические значения tcp_congestion_control и default_qdisc.
6. Сохранить результат в итоговом отчёте.

BBR — настройка TCP congestion control, а не гарантия повышения скорости в каждом
сценарии. Проект не должен обещать конкретную прибавку скорости. Если ядро не
поддерживает BBR, скрипт должен сообщить об этом честно.

6.9. security.sh — минимальная безопасность
-------------------------------------------

Первая версия должна применять только безопасные, обратимые и проверяемые
улучшения. Например:

- не устанавливать слабые или заранее известные пароли;
- использовать уникальные учётные данные, создаваемые официальным установщиком;
- защищать файлы, содержащие секреты, правами root-only;
- поддерживать актуальные системные сертификаты;
- не оставлять временные архивы и файлы с секретами доступными всем пользователям;
- не отключать SSH-парольную аутентификацию, root login или не менять SSH-порт
  автоматически в первой версии;
- не обещать защиту от всех видов атак только за счёт установки firewall.

Более жёсткий SSH hardening — отдельный opt-in сценарий после добавления проверки
ключевого доступа и безопасного rollback. По умолчанию текущую рабочую SSH-сессию
нельзя ставить под угрозу.

6.10. verify.sh — проверка результата
-------------------------------------

Проверяет как минимум:

- служба x-ui существует и активна;
- systemd видит ожидаемую службу;
- установленная панель имеет доступные данные для входа/штатного получения доступа;
- локальный firewall находится в ожидаемом состоянии;
- SSH-порт разрешён правилами firewall;
- BBR включён или честно помечен как неподдерживаемый;
- настройки sysctl сохраняются для последующей загрузки, если включение удалось;
- настроенные порты присутствуют в локальных правилах;
- обязательные файлы и каталоги существуют с ожидаемыми правами.

Проверка TCP-порта с самого сервера не всегда доказывает внешнюю доступность.
Итоговый отчёт должен отличать «служба запущена локально» от «доступ из интернета
подтверждён». Проверка извне может потребовать отдельного клиента или сервиса и
не должна выдаваться за выполненную без соответствующей проверки.

===============================================================================
7. ПОРЯДОК ВЫПОЛНЕНИЯ УСТАНОВКИ
===============================================================================

Рекомендуемый pipeline:

Этап 0. Bootstrap
  Скачать версионированный комплект проекта, проверить контрольную сумму,
  подготовить временный каталог и запустить главный установщик.

Этап 1. Preflight
  Проверить права root, ОС, архитектуру, systemd, apt, сеть и свободное место.
  Определить, чистый ли сервер и нет ли конфликтующих сервисов.

Этап 2. Инвентаризация
  Узнать SSH-порт, активный firewall, текущие правила, состояние BBR и возможную
  предыдущую установку 3x-ui. Сохранить снимок информации до изменений.

Этап 3. План изменений
  Рассчитать необходимые правила/параметры. В интерактивном режиме показать
  опасные изменения. При неоднозначном состоянии — остановиться.

Этап 4. Зависимости
  Обновить индекс пакетов и установить только нужные инструменты.

Этап 5. Минимальная подготовка безопасности
  Защитить каталог и лог, не менять доступ по SSH без отдельного согласия.

Этап 6. 3x-ui
  Запустить официальный установщик с закреплённой версией/режимом, сохранить
  результат установки и проверить наличие службы.

Этап 7. Firewall
  Разрешить сначала SSH, затем порт панели и выбранные inbound-порты; только
  после проверки применить политику firewall.

Этап 8. BBR
  Проверить наличие поддержки, применить настройки и проверить итоговые значения.

Этап 9. Verification
  Проверить службу, настройки, firewall, BBR и доступные данные панели.

Этап 10. Final report
  Вывести результат каждого этапа, адрес панели, место защищённых данных
  аутентификации и путь к журналу. Не печатать секреты в лог.

Примечание: фактический порядок может измениться, если тестирование покажет, что
нужно сначала определить порт панели или установить 3x-ui до расчёта всех правил.
Обязательное правило остаётся неизменным: SSH разрешается до применения deny
incoming; проверка следует после установки; ошибка критического этапа останавливает
следующие несовместимые действия.

===============================================================================
8. ОБРАБОТКА ОШИБОК
===============================================================================

Установка должна завершаться с ненулевым кодом при критическом сбое. Сообщение
должно включать название этапа, краткую причину и путь к подробному журналу.

Типовые случаи:

- неподдерживаемая ОС/архитектура — отказ до изменений;
- нет root-доступа — отказ до установки;
- apt не может обновить индекс — понятная ошибка;
- GitHub недоступен — повтор с ограниченным числом попыток и паузой;
- загрузка релизного архива неполная — удалить временный файл и завершить ошибкой;
- контрольная сумма не совпала — не запускать архив, завершить ошибкой;
- 3x-ui уже стоит — безопасно распознать текущую установку; не переустанавливать
  поверх неё без явного действия пользователя;
- установщик 3x-ui изменился — завершить ошибкой, если больше нельзя надёжно
  получить состояние/учётные данные;
- активный неизвестный firewall — не сбрасывать и не включать другую систему поверх;
- SSH-порт неизвестен — спросить или завершиться до изменения firewall;
- BBR недоступен — предупреждение и запись в отчёт, если остальные шаги безопасны;
- служба x-ui не запустилась — собрать статус и journalctl, не объявлять успех;
- повторный запуск — не дублировать sysctl-файлы, правила и записи конфигурации.

Повторные попытки допустимы для сетевых загрузок и некоторых временных ошибок,
но ограничиваются по числу и времени. Установщик не должен бесконечно повторять
команду, которая заведомо не может выполниться.

===============================================================================
9. ПОВТОРНЫЙ ЗАПУСК И ОБНОВЛЕНИЕ
===============================================================================

9.1. Идемпотентность
--------------------

При повторном запуске MVN Deploy должен определить собственные предыдущие действия.
Он не должен без предупреждения:

- переустанавливать 3x-ui;
- сбрасывать логин/пароль панели;
- удалять пользовательские inbound;
- перезаписывать базу данных панели;
- дублировать правила firewall;
- добавлять повторяющиеся строки в sysctl-конфигурацию;
- менять неизвестные настройки SSH.

Если система уже соответствует целевому состоянию, модуль должен сообщить, что
изменений не требуется.

9.2. update.sh
--------------

В первой версии update.sh должен обновлять именно файлы и логику MVN Deploy до
выбранного релиза. Обновление MVN Deploy и обновление 3x-ui — разные операции.

Обновление 3x-ui должно выполняться штатным поддерживаемым механизмом 3x-ui, а не
путём ручной замены бинарников Xray. Если интеграция обновления 3x-ui будет добавлена
позже, она должна быть отдельной явной командой/опцией, с резервной копией данных
и понятным предупреждением.

Перед обновлением MVN Deploy следует:

- проверить целевую версию и совместимость;
- загрузить и проверить комплект проекта;
- сохранить резервную копию конфигурации MVN Deploy;
- сохранить текущие правила/параметры, созданные MVN Deploy;
- не заменять данные 3x-ui;
- остановиться, если контрольная сумма не совпадает.

===============================================================================
10. UNINSTALL И ОТКАТ
===============================================================================

Удаление потенциально опасно, потому что панель может содержать пользовательские
настройки и базу. Поэтому uninstall.sh не должен быть обычной «обратной кнопкой»,
которая стирает всё без разбора.

Политика первой версии:

- удалить/отключить только файлы и настройки, однозначно принадлежащие MVN Deploy;
- не удалять 3x-ui, базу данных панели или конфигурации Xray без отдельного
  явного подтверждения;
- перед удалением панельных данных создать резервную копию и показать путь;
- не удалять firewall-правила, если нельзя доказать, что их создал именно MVN Deploy
  и что их удаление не нарушит работу сервера;
- не удалять системные пакеты, которые могут использоваться другими приложениями;
- объяснить, какие изменения будут сохранены, а какие будут отменены.

Rollback при сбое установки должен быть ограниченным и безопасным. Не следует
пытаться автоматически полностью «вернуть VPS как был», если для этого нужно
восстанавливать неполный снимок неизвестных правил или конфигураций.

===============================================================================
11. БЕЗОПАСНОСТЬ И СЕКРЕТЫ
===============================================================================

11.1. Скачивание и запуск кода
------------------------------

Однострочный установщик исполняет удалённый код с root-привилегиями — это
существенный риск цепочки поставки. Поэтому проект должен:

- использовать официальный GitHub-репозиторий MVN Deploy;
- публиковать release/tag и не считать изменяемую main надёжной фиксированной версией;
- проверять целостность скачанного архива по SHA-256 или более сильной схеме;
- не исполнять непроверенный/неполностью скачанный архив;
- не скачивать shell-скрипты из случайных зеркал;
- документировать, какие внешние проекты вызываются.

Проверка контрольной суммы гарантирует целостность относительно ожидаемой суммы,
но сама по себе не доказывает доброкачественность источника. Поэтому важны контроль
релизов, защита GitHub-аккаунта и проверка изменений в исходниках.

11.2. Доступы к панели
----------------------

- Использовать уникальные данные, генерируемые официальным установщиком 3x-ui.
- Не добавлять заданные проектом универсальные логин/пароль.
- Не отправлять учётные данные в Telegram, внешние API или сторонние сервисы.
- Файлы с доступами хранить с правами только для root (например, chmod 600) и
  в каталоге, недоступном обычным пользователям.
- Не включать файл с доступами в Git, репорт об ошибке или обычный log.
- В документации явно объяснить способ посмотреть/сбросить доступы через штатную
  команду управления 3x-ui, если это требуется.
- Случайный web path полезен как дополнительная мера, но не заменяет пароль,
  актуальность ПО и правила ограничения доступа.

11.3. SSH
---------

Сохранить текущую сессию SSH недостаточно — firewall должен позволять последующие
подключения после выхода. Перед потенциальным изменением правил нужно определить
порт SSH и добавить соответствующее разрешение. Нельзя автоматически менять порт,
отключать парольную аутентификацию или запрещать root login в первой версии.

11.4. Системные настройки
-------------------------

Изменения sysctl должны быть ограниченными, сохраняться в отдельном файле и иметь
понятный способ проверки. Проект не должен массово переписывать системные файлы,
отключать IPv6 или менять TCP-параметры «ради оптимизации» без необходимости.

===============================================================================
12. ТЕСТИРОВАНИЕ И КРИТЕРИИ ГОТОВНОСТИ
===============================================================================

Нельзя считать проект готовым только потому, что bash -n проходит без ошибок.
Нужны проверки синтаксиса, статический анализ и тестирование на disposable VPS.

12.1. Проверки в Git Bash/на рабочем ПК
--------------------------------------

- bash -n для всех .sh-файлов;
- ShellCheck для Bash-скриптов;
- проверка пробелов/окончаний строк через .gitattributes;
- проверка git diff --check;
- проверка, что секреты/реальные IP/пароли не закоммичены;
- проверка кода возврата всех этапов и обработчика ошибок;
- тесты в безопасной среде для функций, которые возможно протестировать без root.

Важно: Git Bash в Windows не воспроизводит поведение настоящей Linux-системы с
systemd, UFW, sysctl и пакетным менеджером apt. Полную установку нельзя считать
проверенной только в Windows.

12.2. Проверки в тестовом VPS
-----------------------------

Каждый тест проводить на временном VPS или снимке, а не сразу на рабочем сервере.
Минимальная матрица:

1. Чистый Debian — успешная установка.
2. Чистый Ubuntu — успешная установка.
3. Поддерживаемая arm64-система, если заявлена поддержка.
4. Неподдерживаемая ОС — безопасный отказ до изменения firewall.
5. Запуск без root — отказ без изменений.
6. Неверный URL/ошибка GitHub — остановка с понятным сообщением.
7. Неполная загрузка/неверная checksum — архив не исполняется.
8. Уже установленная 3x-ui — предупреждение, никаких непрошеных изменений.
9. UFW уже активен — правила не стираются.
10. Другой firewall — отказ от автоматического конфликта или безопасная обработка.
11. SSH работает на нестандартном порту — после установки доступ не теряется.
12. BBR не поддерживается — корректное предупреждение.
13. Успешное включение BBR — значения и постоянная настройка подтверждены.
14. Ошибка запуска x-ui — установка не сообщает об успехе.
15. Повторный запуск — не создаёт дубликатов.
16. Перезагрузка VPS — панель продолжает запускаться.
17. Проверка прав файлов, содержащих доступы и журнал.
18. Откат/удаление — панельные данные не удаляются без отдельного подтверждения.

12.3. Критерии готовности MVP
-----------------------------

- Полная установка на поддерживаемом чистом VPS завершилась без ручного редактирования
  скриптов на сервере.
- Официальная 3x-ui установлена и её служба активна.
- Панельные доступы можно получить безопасно.
- SSH-доступ сохраняется после настройки firewall.
- Firewall включает только нужные и объяснимые правила.
- BBR подтверждён либо отображено честное предупреждение о неподдержке.
- После reboot служба поднимается автоматически.
- Повторный запуск не повреждает существующую настройку.
- Ошибки критических этапов не маскируются.
- Документация совпадает с фактическим поведением.
- Есть проверенные release-инструкции и журнал изменений.

14. ПЛАН РАЗРАБОТКИ

Этап A. Привести текущий репозиторий к целевой архитектуре

- Проверить install.sh и config/defaults.conf.

- Убрать из рабочего сценария генератор собственного Reality config.
- Убрать отдельный xray.service, созданный нашим проектом.
- Не удалять историю Git: прежние эксперименты остаются в истории, а актуальные
  файлы можно удалить отдельным понятным коммитом.

Этап B. Bootstrap и базовые проверки
------------------------------------

- Сделать рабочую загрузку полной версии проекта.
- Сделать надёжную обработку root/ОС/архитектуры.
- Добавить блокировку повторного/параллельного запуска.
- Унифицировать logger и формат ошибок.

Этап C. Официальная установка 3x-ui
-----------------------------------

- Проверить текущий официальный способ установки.
- Закрепить версию или поддерживать понятную политику выбора версии.

- Проверить способ получения результата/доступов для выбранной upstream-версии.
- Проверить systemd-службу и лог ошибки.

Этап D. Firewall безопасно
--------------------------

- Реализовать обнаружение SSH-порта.
- Реализовать безопасную работу с UFW и обнаружение конфликтующих firewall.
- Сформировать минимум правил для SSH, панели и желаемых inbound-портов.

Этап E. BBR и верификация

Этап F. Документация и качество

- Проверка на чистых тестовых VPS.

Этап G. Первый релиз
--------------------

- Выбрать версию (например, v1.0.0 после успешного тестирования).

   если они больше нигде не используются.
4. Удалить или переименовать users.sh, если он предназначен для ручного управления
   клиентами — клиентами должен заниматься 3x-ui.
5. Перепроверить defaults.conf: удалить неиспользуемые REALITY_DEST,
   REALITY_SERVER_NAME, XRAY_CONFIG_FILE и другие параметры самостоятельного Xray.
6. Обновить README и документацию, чтобы они описывали настоящий pipeline.
7. Добавлять изменения отдельными коммитами и тестировать после каждого блока.

Историю коммитов переписывать не нужно. Нормально оставить ранние коммиты как этап
разработки, а целевой архитектурный переход оформить новым коммитом.

16. РИСКИ И ОГРАНИЧЕНИЯ
===============================================================================

- Установка изменяет системные настройки и требует root-привилегий.
- Firewall способен отрезать SSH-доступ, если неверно определить SSH-порт или
  применить правила в неправильном порядке.
- VPS-провайдер может фильтровать порты внешним firewall, независимо от UFW.
- Поведение официального установщика 3x-ui может меняться; его интерфейс и формат
  результата требуют повторной проверки.
- BBR зависит от возможностей ядра и доступных sysctl-параметров.
- Git Bash в Windows не эмулирует systemd/apt/UFW и не является средой полной проверки.
- Однострочная установка из GitHub требует защиты от подмены исходников.
- Наличие 3x-ui/Xray не означает, что уже создан inbound или клиент. По текущему
  замыслу конфигурация VPN выполняется затем в интерфейсе 3x-ui.
- После создания новых inbound-портов пользователь может понадобиться дополнительно
  открыть соответствующие порты в локальном и/или внешнем firewall.
- Скорость соединения не гарантируется только включением BBR.

18. ФИНАЛЬНОЕ ОПРЕДЕЛЕНИЕ УСПЕХА
===============================================================================

MVN Deploy считается готовым к первому стабильному релизу не тогда, когда скрипт
просто запускается, а когда на чистом поддерживаемом VPS он повторяемо выполняет
следующее:

- корректно определяет систему;
- безопасно устанавливает 3x-ui официальным способом;
- не создаёт параллельную независимую инсталляцию Xray;
- оставляет доступ по SSH;
- применяет только нужные правила firewall;
- включает BBR при наличии поддержки и проверяет состояние;
- подтверждает статус службы и показывает путь к журналу;
- безопасно сообщает, как получить доступ к панели;
- не создаёт VPN-клиентов, QR-кодов и собственных ссылок;
- не повреждает установленную панель при повторном запуске;
- честно сообщает обо всех пропущенных, неуспешных и неподдерживаемых этапах.

Ключевая формула проекта:

  MVN Deploy = безопасная автоматизация подготовки VPS
                + официальный 3x-ui/Xray
                + firewall и BBR
                + проверка результата

Не собственная VPN-панель. Не отдельный Xray-менеджер. Не генератор клиентских
ссылок. Одна команда для получения подготовленного, проверенного сервера.

ДОПОЛНЕНИЕ 19 октября 2026 года: HTTPS, порт панели, fail2ban
===============================================================================

По решению владельца проекта в область ответственности добавлены:

1. Выбор порта панели 3x-ui при установке (флаг --panel-port / MVN_XUI_PANEL_PORT; без выбора — случайный порт установщика).
2. HTTPS панели для домена и для голого IP: Let's Encrypt через официальный установщик 3x-ui (режимы ip и domain) либо
   самоподписанный сертификат (selfsigned). Результат проверяется по ответу панели; если сертификат Let's Encrypt не выдан,
   применяется MVN_XUI_SSL_FALLBACK (по умолчанию selfsigned). Порт 80 в UFW открывается только в режимах ip и domain.
3. Fail2ban для SSH: один файл /etc/fail2ban/jail.d/mvn-deploy.local; пользовательский jail [sshd] не перезаписывается;
   текущий SSH-адрес администратора добавляется в ignoreip. Вход в панель fail2ban не защищает.

Правила остаются прежними: существующую панель 3x-ui скрипт не перенастраивает, SSH-настройки не меняет.
